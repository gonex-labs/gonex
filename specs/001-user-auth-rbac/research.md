# Phase 0 研究：多用户登录与角色权限管理

**关联计划**：[plan.md](./plan.md) | **关联规格**：[spec.md](./spec.md)

本阶段技术上下文中不存在遗留的 [NEEDS CLARIFICATION] 标记（规格与澄清阶段已解决
所有产品层面的歧义）。以下是为落实规格所需做出的架构/实现层面技术决策研究。

## 决策 1：身份凭证机制——数据库持久化的不透明会话令牌，而非无状态 JWT

**决策**：登录成功后签发一个随机生成的不透明令牌（如 32 字节随机数的 Base64
编码），令牌本身不携带信息，服务端将其哈希后连同用户 ID、签发时间、过期时间、
客户端信息存入数据库 `sessions` 表；每次请求校验时查表验证有效性。

**理由**：
- spec.md 已明确要求"身份凭证的有效性 MUST NOT 依赖 gonex 服务进程的持续运行"
  且"服务重启后仍然有效"——数据库持久化天然满足该要求，无需额外考虑 JWT 签名
  密钥的持久化与轮换问题。
- spec.md 要求支持"登出"（会话失效）与"同一账号多并发会话互不踢出"——数据库
  存储可以直接按会话粒度删除或标记失效，语义清晰；纯无状态 JWT 若要支持登出通常
  仍需一个吊销列表，等价于引入了状态存储，不如直接采用有状态会话简单。
- gonex 本身已经依赖数据库（MySQL/PostgreSQL/SQLite），复用现有存储不增加新的
  基础设施依赖。

**考虑过的替代方案**：
- 无状态 JWT：签发自包含、可离线验证的令牌。优点是校验无需查库；缺点是登出/
  吊销困难，且需要额外管理签名密钥的持久化与轮换，与"重启后仍有效"的要求叠加后
  复杂度不降反升，故不采用。
- JWT + Redis 吊销列表：引入 Redis 作为新的外部依赖，与宪法原则 V"固定技术栈"
  相悖（未列入允许的技术栈），故不采用。

## 决策 2：密码哈希算法——bcrypt

**决策**：使用 `golang.org/x/crypto/bcrypt`，默认 cost 因子采用库推荐的安全默认值
（可通过配置调整）。

**理由**：bcrypt 是 Go 生态中最广泛使用、经过长期审计的密码哈希方案，`x/crypto`
为官方扩展库，符合宪法原则 I"遵循 Go 社区规范"。相比手工实现的哈希方案，bcrypt
自带加盐与可调的计算成本，直接满足 FR-002"加盐哈希存储"的要求。

**考虑过的替代方案**：
- Argon2id（`x/crypto/argon2`）：安全性更高、可抵御 GPU 破解，但需要额外调优
  内存/并行度参数，对 MVP 阶段而言复杂度收益比不如 bcrypt；后续如有更高安全
  合规要求可平滑迁移（哈希值中已包含算法标识，可支持双算法共存过渡）。

## 决策 3：SQLite 驱动——modernc.org/sqlite（纯 Go 实现）

**决策**：SQLite 后端使用 `modernc.org/sqlite`，而非依赖 CGO 的
`mattn/go-sqlite3`。

**理由**：宪法原则 III 要求 gonex 是"单一、可独立运行的可执行文件"。CGO 依赖会
显著增加交叉编译的复杂度（需要目标平台的 C 工具链），并可能导致某些目标平台无法
产出静态单一二进制。`modernc.org/sqlite` 是纯 Go 实现，可保持 `CGO_ENABLED=0`
下的静态编译能力，与 MySQL（`go-sql-driver/mysql`，纯 Go）、PostgreSQL
（`jackc/pgx/v5`，纯 Go）驱动的技术特性保持一致。

**考虑过的替代方案**：
- `mattn/go-sqlite3`：生态更成熟、性能略优，但依赖 CGO，与"单文件独立部署"的
  目标冲突，故不采用。

## 决策 4：多数据库方言的 sqlc/goose 组织方式

**决策**：按数据库方言分别维护迁移与查询目录（`db/migrations/{postgres,mysql,
sqlite}`、`db/queries/{postgres,mysql,sqlite}`），`sqlc.yaml` 中为三个方言分别
配置一个 `sql` 条目，各自生成到 `internal/store/{postgres,mysql,sqlite}` 包；
应用层通过一个公共的仓储接口（Go interface）屏蔽方言差异，`internal/store` 顶层
根据配置文件中指定的数据库类型选择对应实现注入。

**理由**：三种数据库在 DDL 语法（如自增主键、时间类型、布尔类型）与部分 SQL
方言上存在差异，无法用完全相同的 `.sql` 文件生成三套代码；分目录维护可以让
每个方言的 SQL 保持地道、可读，同时通过统一的 Go interface 保证宪法原则 V
"三者功能行为必须保持一致"——由集成测试矩阵（对三种数据库运行同一套测试用例）
来保证行为一致性，而非依赖 SQL 文本一致。

**考虑过的替代方案**：
- 使用 ORM（如 GORM）屏蔽方言差异，用一套代码适配三种数据库：与宪法原则 V
  "MUST 使用 sqlc + goose"直接冲突，不采用。
- 只写一套"最大公约数" SQL 强行兼容三种方言：会牺牲可读性和部分数据库的原生
  能力（如 PostgreSQL 的 `RETURNING`），且历史经验表明方言兼容的 SQL 极易在
  边界场景出现细微行为差异，不采用。

## 决策 5：权限校验中间件设计

**决策**：gin 中间件链顺序为：`认证中间件`（解析并校验会话令牌，注入当前用户与
角色到请求上下文）→ `权限校验中间件`（依据转发规则匹配的路径+方法查找所需权限，
校验当前用户角色的权限并集是否覆盖）→ `审计中间件`（对敏感操作与登录事件记录
审计日志）→ `转发处理器`（`net/http/httputil.ReverseProxy` 将请求转发到下游
业务服务）。

**理由**：将认证、授权、审计、转发拆分为独立、可单独测试的中间件，符合 Go 社区
惯用的 gin 中间件组织方式，同时满足宪法原则 VI"权限校验 MUST 在转发之前完成"。

**考虑过的替代方案**：将权限校验逻辑内嵌在转发处理器中：耦合度高，难以单独进行
契约测试，不采用。

## 决策 6：登录失败锁定的数据存储位置

**决策**：在 `users` 表中直接增加 `failed_login_attempts`（失败次数计数）与
`locked_until`（锁定到期时间，可为空）两个字段，而非单独建表。

**理由**：登录失败锁定状态与用户账号强绑定、生命周期一致（用户被删除则锁定状态
随之消失），字段量小，直接存于 `users` 表可减少一次关联查询，实现更简单，且三种
数据库对"可为空的时间戳"字段的支持一致，不引入方言差异风险。

**考虑过的替代方案**：单独的 `login_attempts` 流水表：可保留更详细的失败历史，
但当前规格（FR-004）只要求"计数达到阈值触发锁定、到期自动解除"，不要求保留失败
明细的可查询审计（登录失败事件已经通过 FR-010 的审计日志覆盖），故 MVP 阶段选择
更简单的实现。

## 输出

以上 6 项技术决策均已给出结论，Phase 0 完成，可进入 Phase 1 设计。
