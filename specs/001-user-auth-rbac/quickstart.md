# 快速验证指南：多用户登录与角色权限管理

**关联计划**：[plan.md](./plan.md) | **关联规格**：[spec.md](./spec.md)

本指南描述如何端到端验证本功能在实现完成后是否按预期工作，覆盖 spec.md 中
四个用户故事的核心路径。具体接口字段参见 [contracts/](./contracts/)，数据结构
参见 [data-model.md](./data-model.md)。

## 前置条件

- 已构建 gonex 可执行文件（单一静态二进制）。
- 准备一份最小 YAML 配置文件，指定：
  - 数据库类型与连接信息（MySQL / PostgreSQL / SQLite 三选一）
  - 监听地址与端口
  - 至少一条转发规则（`path_pattern`、`method`、`upstream_url`）
- 已执行数据库迁移（对应所选数据库方言的 `goose up`）。
- 准备一个用于接收转发请求的简单下游 HTTP 服务（例如返回固定 JSON 的测试
  服务），并在配置的转发规则中指向它。

## 场景 1：初始化超级管理员并登录（对应用户故事 1）

1. 执行初始化命令创建首个超级管理员账号（例如
   `./gonex admin init --login-id admin --password <初始密码>`，具体命令名以
   实现阶段的 CLI 设计为准）。
2. 调用 `POST /api/gonex/auth/login`，传入正确的 `login_id`/`password`。
   **预期**：返回 `200`，响应体含 `token` 与 `expires_at`。
3. 使用错误密码重复步骤 2。
   **预期**：返回 `401`，且错误提示不区分"账号不存在"与"密码错误"。
4. 连续 N 次（N 为配置的失败阈值）使用错误密码登录。
   **预期**：达到阈值后返回 `403`（账号锁定）；等待锁定时长到期后，使用正确
   密码登录应恢复 `200`（无需人工解锁，对应澄清记录）。

## 场景 2：创建用户、角色并分配权限（对应用户故事 2）

1. 使用步骤 1 中超级管理员的 `token`，调用 `POST /api/gonex/permissions`
   创建一个权限项（如 `path_pattern=/api/orders, method=GET`）。
2. 调用 `POST /api/gonex/roles` 创建一个角色，并关联上一步的权限项。
3. 调用 `POST /api/gonex/users` 创建一个新用户，并在 `role_ids` 中指定该
   角色。
   **预期**：返回 `201`，新用户可使用设置的初始密码登录（重复场景 1 步骤 2）。
4. 调用 `PATCH /api/gonex/users/{id}` 将该用户 `is_enabled` 设为 `false`。
   **预期**：该用户后续登录返回 `403`（账号已禁用）。

## 场景 3：权限校验与请求转发（对应用户故事 3）

1. 使用场景 2 中创建的、具有 `/api/orders GET` 权限的用户登录，获取 `token`。
2. 使用该 `token` 请求 `GET /api/orders`（假设配置的转发规则将其指向下游
   测试服务）。
   **预期**：返回下游服务的响应内容（请求被成功转发）。
3. 使用同一 `token` 请求一个未被授权的路径（如配置了权限校验但该用户角色未
   包含对应权限的路径）。
   **预期**：返回 `403`，且验证下游测试服务未收到该请求（未被转发）。
4. 不携带 `Authorization` 头请求任意受保护路径。
   **预期**：返回 `401`。
5. 临时停止下游测试服务，重复步骤 2。
   **预期**：返回 `502`/`504`，请求不会长时间挂起。

## 场景 4：审计日志追溯（对应用户故事 4）

1. 使用超级管理员 `token` 调用 `GET /api/gonex/audit-logs`。
   **预期**：能查询到场景 1～3 中产生的 `login_success`、`login_failed`、
   `user_create`、`role_create`、`user_update` 等审计记录，且每条记录含
   操作人、操作时间、操作内容。
2. 修改场景 2 中角色的权限配置，再次查询审计日志。
   **预期**：能看到对应的 `role_permission_update` 记录及权限变更摘要。

## 跨数据库一致性验证

对 MySQL、PostgreSQL、SQLite 三种数据库分别重复场景 1～4（可通过 CI 矩阵化
执行），预期结果 MUST 完全一致，以验证宪法原则 V"三种数据库行为必须保持一致"
的要求。

## 会话持久性验证（对应 FR-003 澄清项）

1. 完成场景 1 的登录，获得 `token`。
2. 重启 gonex 服务进程（不清空数据库）。
3. 使用同一 `token` 请求任意受保护接口。
   **预期**：请求成功，无需重新登录，验证凭证有效性不依赖服务进程存活。
